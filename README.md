# rucc-postgres

A harness that builds a pinned, unmodified PostgreSQL release with [rucc](https://github.com/tamnd/rucc) and with a reference compiler, runs Postgres's own test suites against both, and records what happened in files that outlive any one report.

Postgres is one project, but a large one: about 1.8 million lines of C under `src` and `contrib`, a configure step that asks the compiler hundreds of questions, atomics, inline assembly, per function target attributes for CRC and popcount, and `sigsetjmp` under every error path. [rucc-real-corpus](https://github.com/tamnd/rucc-real-corpus) grades rucc on a ladder of whole projects. This repository does the same for one project that is too big to be a rung, with a harness shaped around it: per test records instead of per project ones, baselines per platform, and a map of what the tree asks of a compiler.

## The rules

**No compiler code.** Nothing here compiles C. Every compile goes to a real compiler, rucc or the reference, through a shim that only records. A fix that belongs in rucc goes to rucc.

**No Postgres patches.** The bytes that come out of the pinned tarball are the bytes the compiler sees. There is no patches directory, and a configuration file can hold only documented `configure` and meson options, which the loader checks. A build that needs an edit to get further is a finding against rucc, not a configuration.

**No copied Postgres files.** Postgres is downloaded, verified and unpacked into a cache outside the repository. Nothing from its tree is committed here, not a header, a test or an expected output.

**No reductions.** When rucc gets something wrong, cutting the failing file down to a small case is work for rucc's own test suites, and the case lives there. This repository only says which file, which test and which probe.

## Commands

The harness is one binary, `rpg`, plus the shim `rpg-cc` that has to sit next to it, and `rpg-ar`, an `ar` that writes its archives with rucc's archive writer. It is run from anywhere inside the checkout and finds the root by walking up to `pins.toml`, or from `RPG_ROOT`.

```
cargo build --release
target/release/rpg fetch                       download REL_18_6, check its SHA-256 twice, unpack it
target/release/rpg build --cc gcc-16           configure and build with the minimal configuration, through the shim
target/release/rpg build --cc ~/rucc/target/release/rucc --system autoconf --level -O0
target/release/rpg test --suite regress        run the main regression suite against the only build in work/
target/release/rpg test --out work/DIR --row L64   the same for a named build, graded against the L64 baseline
target/release/rpg baseline --row L64          build with the row's reference compiler and run the suites three times
target/release/rpg demands                     scan the tree and rewrite demands.toml
target/release/rpg config-diff --a work/A --b work/B   compare what two configured trees decided, less config-divergences.toml
target/release/rpg repro --build work/DIR --file src/backend/parser/gram.c   bundle one translation unit for a bug report
target/release/rpg asm-audit                   list every inline assembly statement and rewrite asm-audit.toml
target/release/rpg frames --a work/A --b work/B   compare every function's stack frame between two builds
target/release/rpg triage --out work/DIR       group a run's failures and cores by what went wrong first
target/release/rpg mixed --gcc work/A --rucc work/B   find the object, then the transformation, a failure comes from
target/release/rpg nightly --nights DIR         keep a night's rows in runs/ and say what got worse
target/release/rpg bench --out work/DIR         time pgbench, the analytic set and the regression suite against one build
target/release/rpg bench-compare --a work/A --b work/B   say how much faster or slower b's server is than a's
target/release/rpg bench-night --gcc DIR --rucc DIR   keep a night's bench in runs/bench and say what got worse
target/release/rpg profile --out work/DIR       count where one build's server spends its cycles under the same loads
target/release/rpg profile-compare --a work/A --b work/B   list the functions where b's server spends more than a's
```

`rpg fetch` downloads with curl into `RPG_CACHE`, or `~/.cache/rpg`. The archive's SHA-256 has to match `pins.toml` every time it is used, including from the cache, and on a fetch it also has to match the `.sha256` file the Postgres project publishes next to the tarball, which catches a pin written down wrong.

`rpg build` takes `--cc`, `--level -O0`, `-O1`, `-O2` (the default), `-Os` or `-O2-flto`, which adds `-flto` to every compile and link (`b_lto` under meson, `CFLAGS` and `LDFLAGS` under autoconf), `--system meson` (the default) or `autoconf`, `--config minimal` (the default) or `full`, `--out DIR`, `--jobs N`, `--twice` and `--configure-only`, which stops after configure or meson setup so that two compilers' answers can be compared without building either. `--linker NAME` puts `-fuse-ld=NAME` on every link, in `c_link_args` under meson and in `LDFLAGS` under autoconf, for a linker other than the one the compiler picks itself, and `build.json` records it. `--ar PATH` sets `AR` and `RANLIB` to that program for configure or meson setup, which keep it, and `build.json` records that too. The build directory defaults to `work/<pin>-<config>-<system>-<level>-<compiler>` and holds `configure.log`, `build.log`, the Postgres build tree under `build/`, `compile.jsonl`, `compile_commands.json` and `build.json`, which says what was built with what, how long each step took, and where the build stopped if it stopped. `RPG_PREFIXES` is a colon separated list of prefixes with an `include` and a `lib` beneath each, for libraries a machine keeps where the compiler does not look, as Homebrew does on macOS. Each becomes part of `--with-includes` and `--with-libraries` under autoconf, `extra_include_dirs` and `extra_lib_dirs` under meson, and `PKG_CONFIG_PATH`, and `build.json` lists them. The flags in `CFLAGS`, `CPPFLAGS` and `LDFLAGS` are cleared for every build, so this is the way in.

`rpg test` refuses to run as root, because initdb does. `--suite` is `regress`, the default, `isolation`, `ecpg`, `contrib`, `src/test/modules` as `modules`, or `world`. Under meson it runs `meson test --suite setup` and then the suite, for the first three and for `world`, which is every suite but setup with `--num-processes <jobs>`, as upstream's CI runs it. A meson test that runs `pg_regress` gives a record per test, `regress/regress/boolean`, and every other meson test is a TAP script and gives one, `initdb/001_initdb`. Under autoconf it runs `make check` for `regress` and `make -C <dir> check` for the others, with `-k` for `contrib` and `modules` so that one module failing does not stop the rest. Those two are a `pg_regress` run per module, which the log splits at the `# +++ regress check in contrib/amcheck +++` line Postgres's makefiles print ahead of each, and each test is named for its module, `amcheck/check_btree`, or `amcheck/isolation/read-write-unique` for an isolation run. TAP runs are left out of those two. `world` runs `make -k -j<jobs> -Otarget check-world PROVE_FLAGS=--timer` under autoconf, as upstream's CI does, and reads both kinds of run out of its log: each `pg_regress` test is named for its directory, `src/test/regress/boolean`, and each TAP script too, `src/bin/initdb/t/001_initdb.pl`, with the log of a failing script copied next to the diffs. ecpg's run prints no marker, so it is named for the directory make last entered. `PG_TEST_EXTRA` is passed through from the environment, and the `world` workflow sets it to what PG3's exit criterion names. It sets `PG_TEST_TIMEOUT_DEFAULT` from the row, doubled at `-O0`, and under meson passes `--timeout-multiplier` so that meson's own limit of 1000 seconds a test, which upstream sized for the default of 180, grows by the same share. It copies `regression.out`, `regression.diffs` and the server logs of each run into `results/<suite>/run-<n>/`, and appends one line per test to `records.jsonl`. A failing test is `crashed` rather than `failed` when the postmaster log says a backend was terminated by a signal. It exits nonzero when a test fails that the baseline says passes, or any test fails when there is no baseline. A pin in `pins.toml` can list tests as `<suite>/<test>` under `flaky`, for a race in the test itself that upstream fixed after the release. Those count as flaky whatever the baseline says, so they neither fail the run nor open a nightly issue, and the list goes when the pin moves to a release with the fix.

`rpg cross-modules --server A --modules B` runs the loadable modules of build B in the server of build A, which is the ABI test between two compilers, since a module and the server that loads it meet only through the calling convention and the structs they share. Every shared library under `contrib`, `src/pl` and `src/test/modules` that both builds have is copied from B over A's, after A's own are kept in `A/own-modules/`, and each copy is given the current time so that the build does not relink it. Under autoconf the `contrib` and `modules` suites then run in A. Under meson, which has no suite for all of `contrib`, the world suite runs instead, after `tmp_install` is removed so that the copies are the ones installed. A's own libraries are put back afterwards whether the suites passed or not. The records go to A's `records.jsonl` with the suite `cross-contrib`, `cross-modules` or `cross-world`. Both builds have to come from the same build system, pin, commit and configuration. Running it again with the two swapped is the other way round.

`rpg stress` puts a build's server under pgbench and then checks that nothing was lost. It installs the build into its temporary install as the suites do, starts a server on a private socket with a 16MB buffer pool and a checkpoint every 30 seconds, loads pgbench's tables at `--scale` (10 by default), and runs the default TPC-B script with `--clients` clients and threads (twice the cores by default) for `--minutes` (5 by default), half with the simple protocol and half with prepared statements. Every transaction adds the same amount to one account, one teller, one branch and the history, so the four sums have to agree afterwards. It checks them, stops the server with `-m immediate` so that it has to replay its WAL, checks them again, and then reads the server log for a backend killed by a signal, a PANIC or a failed assertion. Each of those is a record in `records.jsonl` under the suite `stress`, the logs stay in `<out>/stress/`, and the data directory is removed when everything passed. It exits nonzero when anything did not pass. PG3 asks for `rpg stress --row L64 --minutes 60`.

`rpg bench` measures how fast a build's server runs, for PG7. It installs the build as `rpg stress` does and starts a server with settings that keep the disk out of it: a 1GB buffer pool, 64MB of `work_mem`, `fsync`, `synchronous_commit` and `full_page_writes` off, no checkpoint for an hour, no autovacuum and no JIT. It loads pgbench's tables at `--scale` (100 by default), runs `select-only` once for up to 30 seconds to bring them into memory, and then runs pgbench's `select-only` and `tpcb-like` scripts in turn with prepared statements and `--clients` clients and threads (one per core by default), `--seconds` each (60 by default), `--runs` times (10 by default). Before each run pgbench vacuums the tables it writes to, so the runs start from the same place.

Then it loads the analytic set at scale factor `--sf` (1 by default) into the same server and times its twenty queries `--runs` times in turn, each through its own `psql`. The set is a TPC-H style schema of eight tables with a generator written in SQL in `crates/rpg/src/analytic/load.sql`, which computes every value from `hashint8` of the row number, so that any two servers that compute correctly load the same rows. At SF 1 that is 1,500,000 orders and about 6,000,000 order lines, close to 3GB on disk with the indexes. The queries in `crates/rpg/src/analytic/queries.sql` are our own in the style of TPC-H's, ordered so that no two rows tie and computed in `numeric`, so their output is the same bytes on every server that gets them right. Each query runs once first to warm up, and what it prints is kept as a fingerprint. A later run that prints something else fails that query.

The server is then stopped, its data directory removed, and the main regression suite is run `--runs` times as `rpg test` runs it and timed by the wall clock, setup included, as `make check` would be. A suite run where a test does not pass ends that measure, since a suite that fails may have skipped work. `--only pgbench`, `--only analytic` or `--only regress` takes one of the three. Every sample goes to `<out>/bench/bench.json` along with the compiler, level, host, clients, scale, scale factor and each query's fingerprint, each measure is a record in `records.jsonl` under the suite `bench` that passes when every run finished, and the command prints the median of each with the interquartile range beside it. It exits nonzero when a measure stopped short.

`rpg bench-compare --a A --b B` reads two `bench.json` files, or the ones under two build directories, and writes a Markdown table of each measure with the median and interquartile range on both sides and how much faster or slower b is. A difference between the medians smaller than the two ranges added together is reported as no measurable difference. A query whose fingerprints differ is reported as giving different answers, which means one of the two servers is wrong, and the queries that both answered the same way are summed up by the geometric mean of their ratios, as PG7 states its bound. The report says so when the two runs differ in more than the compiler, a pin, a configuration, a client count, a scale or a scale factor. `--out FILE` writes the report to a file as well as printing it. Both servers have to run on the same machine for the comparison to mean anything, which the report shows but does not check. The `bench` workflow builds the pin with gcc and with a released rucc at `-O2` under autoconf each night, runs `rpg bench` on both one after the other on one runner at 5 runs of 30 seconds, and puts the comparison in the job summary. Run by hand it takes the full sizes. A shared runner is a noisy machine, so those numbers show the direction and the exit criterion is measured on server3. A pull request that changes how the measures are taken runs it at 3 runs of 20 seconds, scale 10 and SF 0.1.

`rpg profile` says where the time goes. It starts a server as `rpg bench` does, with the same settings, loads pgbench's tables at `--scale` (100 by default) and the analytic set at `--sf` (1 by default), runs each analytic query once, and then profiles three loads: pgbench's `select-only` and `tpcb-like` scripts with `--clients` clients (one per core by default) running `--transactions` transactions each (20,000 by default), and the analytic set once. Each load is a fixed amount of work, so two servers' counts compare directly. A load runs as the workload of `perf record` attached to the postmaster, so the backends it forks for the load are sampled and pgbench and psql are not. It counts `cycles:u` where the machine counts cycles and `cpu-clock:u` where it does not, as on most virtual machines, and `--event` picks another. The samples are summed by function and object, with GCC's clones like `foo.isra.0` and `foo.cold` counted under `foo`, and written to `<out>/profile/profile.json`. `--loads` takes a comma separated list of the three. perf has to be on `PATH`, and Ubuntu's default `kernel.perf_event_paranoid` of 4 has to come down to 2 or less.

`rpg profile-compare --a A --b B` joins two profiles by function and writes a Markdown table per load of the `--top` functions (40 by default) whose counts differ most, sorted by how much more b spent in them than a, with each one's share of the whole difference. That list is what PG7 works through after the register allocator. The `bench` workflow runs `rpg profile` on both servers after the bench and puts the comparison in the job summary too.

`rpg bench-night --gcc DIR --rucc DIR` keeps a night of the `bench` workflow in git. The runner is a different machine each night, so a rucc number alone says little, but how many times as long the rucc server takes as the gcc one on the same machine only moves with the code. It reads the two `bench.json` files, turns each measure into that ratio with its noise beside it, the two interquartile ranges as fractions of their medians added together, sums the analytic queries up by their geometric mean, and writes `runs/bench/<date>.json`. Measures that failed on either side or where the two servers gave different answers are left out and listed. Tonight is compared with the last earlier night run the same way, and a measure whose ratio grew by more than `--threshold` percent (10 by default) and by more than both nights' noise together is a regression. `reports/bench.md` is rewritten with the headline ratios of the last thirty nights, and `--issue FILE` writes the title and body of an issue when something got worse. The workflow commits the night and opens that issue with the `kind/perf` label, in tamnd/rucc when the `RUCC_ISSUES` secret is set and in this repository otherwise, as the `nightly` workflow does.

`rpg triage` reads what `rpg test` kept under `results/` and groups the failures by cause, so that a hundred failures with one cause show up as one group. A test's signature is the crash when the server it ran against crashed, which is the `TRAP:` line of a failed assertion or else the line saying which signal a process died of. Otherwise it is the first line of the test's diff, what it printed that it should not have or else what it should have printed and did not. A TAP script's signature is the first crash in its log or else its first failed test. Numbers become `N` in every signature, so an OID or a PID does not split a group. Core files in `<out>/cores`, or the directory `--cores` names, go to `gdb` with the executable their name gives, which needs `kernel.core_pattern` to have `%E` in it. Each backtrace is written to `<out>/triage/`, and the core is grouped by the signal and the top three functions of the thread that crashed. A core from SIGQUIT is listed apart and not counted, since Postgres sends that signal to every child on an immediate shutdown and to every other backend after one crashes. The report is `<out>/triage.md`, largest group first, and the command exits 0 either way. The `world` workflow sets the core pattern, lifts the core size limit, and points `TEMP_CONFIG` at a file with `log_min_messages = debug1`, which reaches every server under autoconf and every TAP script's server under meson. It then runs the triage after the suites and puts the report in the job summary. On macOS, which writes a crash report and no core, the triage reads the `.ips` reports in `~/Library/Logs/DiagnosticReports`, or the directory `--reports` names, that were written after the build finished (or after `--since`, in seconds since the epoch) by a program under the build directory or one Postgres installs. The faulting thread's frames go to `<out>/triage/` and the crash is grouped by its signal and top three frames, as a core is. On Windows, where a server log says `terminated by exception` rather than by a signal, Postgres writes a minidump itself when its data directory has a `crashdumps` directory. Under meson `rpg test` puts that directory in the initdb template every test cluster is copied from, and moves the dumps written during the run into `results/<suite>/run-<n>/crashdumps/`. The triage gives each one to `cdb` when it is on the path or where the Windows SDK installs it, writes what it says to `<out>/triage/`, and groups the dump by the exception and the top three frames, named from what `postgres.exe` exports. Without `cdb` a dump is still counted, in a group that says it was not read. Postgres writes the dump from inside the dying process and sometimes gives up partway, so the `world` workflow also sets `LocalDumps` in the registry for `postgres.exe`, which has Windows Error Reporting write a dump from outside the process into `results/windows-error-reporting/`. The triage reads those as well, and a crash with a dump of each kind is counted once, by the one Windows wrote.

`rpg nightly` reads a directory of downloaded world artifacts, finds every directory in it that holds a `build.json`, and writes one night file per row to `runs/<date>/<row>-<pin>-<config>-<system><level>.toml`, with `-<linker>` and the archiver's file name at the end for a build that named either, where the row comes from the records when `rpg test` was given `--row`, with the compiler, whether the build got through, the count of each outcome and the list of tests that did not pass. Each row is compared with its last night file from an earlier date. A test that does not pass tonight and was not on that night's list is a regression, and so is a build that stops when the earlier one got through. `reports/nightly.md` is rewritten with the latest night of every row, what got worse and what got better, and the counts of the last thirty nights. With `--issue FILE` it writes the title and body of an issue when anything regressed. The world workflow runs L64 under autoconf and meson, LA64 under autoconf on GitHub's arm runners, M64 under both and W64 under meson in MSYS2, and each row once more at -O2 with the full configuration. The `nightly` workflow runs `rpg nightly` when a scheduled or hand started world run finishes, commits `runs/` and `reports/` to main, and opens the issue in tamnd/rucc when the `RUCC_ISSUES` secret holds a token that can, or in this repository otherwise.

`rpg mixed` takes a gcc build and a rucc build of the same pin, configuration and build system and finds the one object a failure comes from, then the one transformation in it. It works in the gcc build tree. For each trial it copies a chosen set of rucc's objects over gcc's, lets the build system relink, and runs the check, which is `--suite` (the main suite by default) or a shell command given as `--check`. A suite fails a trial when a test fails that failed with every object from rucc and passed with every object from gcc. A command fails it by exiting non zero, and it sees the build tree as `RPG_BUILD`. The objects go in order by path, `--under` keeps only the ones whose C file starts with one of a list of prefixes, and the search finds the first `k` for which the first `k` from rucc fail, then tries that object alone. When rucc built it, the file is then compiled again with `-fpass-fuel-global=<n>`, going up by doubling and back down by halves to the first number of transformations that fails, and compiled once more at `n - 1` and `n` with `-fdump-ir=all` so the first IR dump that differs can be written out as a diff. `--no-fuel` stops after the object. Every gcc object is copied aside first and put back at the end, however the search ends, and the tree is built once more. The report is `mixed.md` in `--out`, which defaults to `mixed/` in the gcc build directory. The `world` workflow runs it on the main suite and on a planted fault, a check that fails whenever one object is exactly rucc's, which has to end at that object and at the last transformation rucc makes in it.

`rpg config-diff` reads `pg_config.h`, the variables `src/Makefile.global` sets and the probe answers from meson's log or configure's output in both trees, with each tree's own paths replaced so that two build directories compare equal. A difference listed in `config-divergences.toml`, or in the file `--divergences` names, is printed as explained along with the reason the entry gives, and an entry that matched nothing is printed so it can be taken out. Every entry has to say why the difference does not change which code is compiled. An entry with `rows` applies only when `--row` names one of them, for a difference that belongs to one platform. The command exits nonzero when any difference is left unexplained. The `world` workflow's `probes` job configures the pin with gcc and with rucc under each build system on L64 and on LA64 and runs it on the two trees with the row given.

`rpg repro` finds the one call in a build's `compile.jsonl` that compiled the named file, which is given relative to the Postgres source tree, or to the build tree for a generated file such as `gram.c`. It writes a bundle directory, by default `repro/<path>` inside the build directory or `--out DIR`, with the preprocessed source `<name>.i`, made by running the recorded command again in the recorded directory with `-E -o` in place of `-c -o` and without the dependency file options, `command.txt` with the recorded command line, directory and environment, `compile.sh`, which compiles the `.i` again with the recorded flags minus `-I`, `-D`, `-U`, `-include`, `-M*` and the other preprocessor options, and `compiler.txt` with the compiler's `--version` and the commit of the checkout it was built in, since `rucc --version` names a release and not a commit. `CC=... compile.sh` runs the same compile with another compiler. When no call compiled the file it says so, and when several did, as for the files of `src/port` that meson builds three times, it lists their objects and `--object PART` picks one. This is what goes with a rucc bug report.

`rpg frames` compares how much stack each function takes in two builds. Postgres checks its own stack depth against `max_stack_depth` and has regression tests that recurse on purpose, so a compiler whose frames are a few times larger than gcc's fails them with `stack depth limit exceeded` while everything else passes. For each of `--a` and `--b` it runs every compile of a C file in `compile.jsonl` again in its recorded directory, with the recorded compiler or the one `--a-cc` or `--b-cc` names, adding `-fstack-usage`, dropping the dependency file options and writing the object to a scratch directory, so the build tree is not touched. It runs `--jobs` compiles at a time, by default one per core. Each function is keyed by the file compiled, the object and the name, so a static function with one name in two files is two entries, and a file compiled several times with different flags, as `src/common` and `src/port` are, is one entry per object. A function with no exact match on the other side is matched by the name before the first dot, which pairs gcc's clones such as `foo.isra.0` with a plain `foo`. The report, `frames/<a>-vs-<b>.md` or `--out FILE`, gives the number of functions matched and found on one side only, the median, 90th and 99th percentile and largest ratio of b over a, the totals and largest frame of each side, and the 50 functions with the largest ratio and the 50 with the largest frame in b, with dynamic frames flagged. It exits 0 either way, since it is a measurement and not a gate. The reports for `REL_18_6` with autoconf and the minimal configuration, rucc 0.11.19 against gcc 16 at `-O0` and `-O2`, are in `frames/`. The `world` workflow measures rucc at `-O2` and at `-O0` against one gcc-14 `-O2` build, which is how PG2's bound is written, and puts both ratio tables in the job summary.

## The shim

`rpg build` copies `rpg-cc` into the build directory as `bin/cc` and `bin/gcc`, puts `bin` first on `PATH`, sets `CC` to it and writes `bin/rpg-cc.toml` naming the real compiler. The shim runs the real compiler with the same arguments and appends one JSON line per call to `compile.jsonl`: the argv, the working directory, the environment variables that change what a compiler does, the SHA-256 of every input and output, wall, user and system time and peak RSS of the child, the exit status or signal, and the first KiB of stderr. It prints nothing of its own, because configure judges a compiler partly by what it writes to stderr.

When the real compiler is rucc, which is anything whose `--version` starts with `rucc `, and rucc understands `-frucc-trace`, the shim adds `-frucc-trace=<tmp>` to every call that compiles C and folds the trace lines, with rucc's own phase and pass timings, into the record under `rucc`. Whether rucc understands the option is probed once per build by compiling a one line file, so an older rucc is simply run without it. `RPG_TWICE=1`, or `rpg build --twice`, compiles every translation unit a second time and fails the call if the two objects differ.

`RPG_REAL_CC`, `RPG_COMPILE_LOG`, `RPG_RUCC_TRACE` and `RPG_TWICE` override the settings file, which makes the shim usable by hand as well.

## The archiver

PG9 asks for a build with rucc's own archiver as `AR`. rucc writes archives with its `rucc-archive` crate, but only out of what it compiles itself under `--emit=archive`, and Postgres's build archives objects it compiled earlier. `rpg-ar` is that step with rucc's writer in it. It takes the `ar crs` and `ar csr` lines autoconf and meson write, reads the names each ELF member defines, and has `rucc-archive` write the file and its symbol index, so every static link of `libpgport.a` and the other archives goes through an index rucc's code wrote. `r` replaces a member of the same name in an archive that is already there and adds the rest, `q` appends, and given only an archive, as `ranlib` is, it checks that the file is one and leaves it alone, since the index is always there. `--version` exits zero, which is how meson recognizes an `ar`. It reads ELF only, so it is for the Linux rows.

## Records

`records.jsonl` has one line per test per run, in the shape of rucc-real-corpus's records with the test as the unit:

```json
{"project":"postgres","pin":"REL_18_6","row":"L64","host":"server3","level":"-O2","system":"autoconf","config":"minimal","suite":"regress","test":"join_hash","outcome":"failed","class":"diff","seconds":4.1,"compiler":"rucc 0.12.3","rucc":"0.12.3","rucc-commit":"abc","reference":"gcc-16.2.0","baseline":"passed","artifacts":"runs/2026-10-14/L64-O2/regress/join_hash/"}
```

`outcome` is one of `passed`, `failed`, `crashed`, `timeout`, `build-failed` and `skipped`. `class` says how a failure failed: `diff`, `tap` or `error`. A run that did not finish, because pg_regress bailed out or meson timed it out, gets an extra line with the test `*`, so that a suite that stopped halfway cannot read as a suite with fewer tests.

## Rows and baselines

`rows.toml` has the four platforms rucc is graded on, each with its reference compiler: L64 (Linux x86-64, gcc-16), LA64 (Linux AArch64, gcc-16), M64 (macOS arm64, Apple clang) and W64 (Windows x86-64 under MSYS2 UCRT64, gcc). `provision/` has a script per row that installs what the minimal configuration and the TAP tests need. The Linux scripts create an unprivileged `pg` user and only touch `kernel.core_pattern` when asked with `--core-pattern`.

`rpg baseline --row L64` builds with the row's reference compiler and runs each suite three times, or `--runs N`. A test that passed every run is `passing`, one that failed every run is `failing`, and one that did both is `flaky`. The sets and the build and test times go to `baselines/<row>/<pin>/<config>/baseline.toml`, next to the records they came from.

The `baseline` workflow does the same on a hosted runner when started by hand, for L64 and LA64 with gcc-14 from Ubuntu, for M64 with Apple clang and for W64 with MSYS2's gcc under meson, and keeps the directory as an artifact. A baseline goes into git by a pull request, so a person reads it before anything is graded against it.

For REL_18_6 there are baselines for L64 minimal, from server2 with gcc-16, for L64 full, LA64 minimal and LA64 full, from the workflow with gcc-14, for M64 minimal and M64 full, from the workflow with Apple clang 17 and Homebrew's libraries, and for W64 minimal and W64 full, from the workflow with MSYS2's gcc 16.2 under meson. All eight passed 231 of 231 regression tests in each of their three runs. The Linux workflow builds took 98 to 102 seconds with 4 jobs, the M64 ones 87 and 96 seconds with 3, and the W64 ones 629 and 659 seconds with 4.

## Demands

`demands.toml` is what the pinned tree asks of a C compiler beyond plain C11, found by a text scan of `src` and `contrib` with comments and literal contents removed: 128 bit integers, overflow, atomic and bit builtins, computed goto, inline assembly, target attributes, x86 and Arm intrinsics, cpuid, `sigsetjmp`, `PGDLLIMPORT` and so on, plus one entry per `__builtin_*` name, per attribute and per `pg_attribute_*` macro. Each entry lists the lines per file. The `rucc-status` and `rucc-issue` fields are for a person to fill in, and `rpg demands` keeps them when it rescans.

It counts what is written, not what one target compiles, and a feature behind a Postgres macro is counted where the macro is defined. It is a map for deciding what to look at, not a proof of what rucc needs.

## Inline assembly

`asm-audit.toml` lists every inline assembly statement under `src` and `contrib`, written by `rpg asm-audit` from a small scanner that skips comments and literals and splits each statement at its colons and commas. Each entry has the file, the line, the function or macro it is in, the `#if` lines around it, the qualifiers, the template, the outputs and inputs with their constraints, the clobbers and any goto labels. The top of the file counts statements per file, kind and qualifier, operands per constraint as written and per constraint letter, and clobbers, since those say what a compiler has to understand. Like `demands.toml` it covers every architecture Postgres supports, and the `guard` lines say which one a statement is for.

For REL_18_6 it finds 43 statements in 6 files: 35 extended, 6 basic (with no operands) and 2 in the MSVC `__asm` form. The output constraints are `=r`, `=&r`, `=q`, `=a`, `=m`, `=&b`, `+m`, `+q`, `+d` and `+R`, the input constraints are `r`, `m`, `i`, `a`, `d`, `rm` and the matching `0`, and the only clobbers are `memory` (33) and `cc` (20). The 16 that are not for another architecture, meaning x86-64 code and code for any architecture, use `=q`, `=m`, `=a`, `+q` and `+m` for outputs, `m`, `a`, `r`, `rm` and `0` for inputs, and `memory` and `cc`.

## Where it stands

PG0, the harness itself. The first runs were on server2, an Ubuntu 24.04 x86-64 machine with 6 shared cores, using gcc-16 16.0.1 (20260315) as the reference, meson and `-j4`:

- `rpg fetch` took 16 seconds, download included, and both hash checks passed.
- The gcc-16 build compiled 1577 translation units: 21 seconds to configure and 202 seconds to build on a quiet machine, 42 and 507 on a busy one, about 620 compiler user seconds either way. The largest compile is `gram.c`, at 218 MB peak RSS.
- The regression suite passed 231 of 231 tests, in 30 to 42 seconds including the temporary install. Three runs for the L64 baseline agreed, so nothing is flaky yet.
- Under meson, rucc 0.11.15 got through configure and compiled all 1073 translation units the backend needs, in 81 seconds and 196 user seconds, peaking at 304 MB on `gram.c`. It stopped at the link of `src/backend/postgres`, the one link meson does through a response file: rucc passed `-Wl,--as-needed` from `@postgres.rsp` to `ld` as it was, while the same option on a command line works.
- Under autoconf, which uses no response files, rucc built the whole of `world-bin`, 1417 translation units with no failures, in 25 seconds of configure and 108 of build. That build passed 231 of 231 regression tests in 45 seconds, and the version string in the `postgres` binary says `compiled by rucc 0.11.15`.
- `rpg config-diff` between the two meson trees shows rucc's configure answers differing in 9 `pg_config.h` defines. rucc answers no to the probes for `__get_cpuid`, `__get_cpuid_count`, the SSE 4.2, AVX-512 and XSAVE intrinsics and the `popcntq` inline assembly, so Postgres falls back to slicing by 8 CRC32C and no runtime popcount check. The other differences are the compiler version string and a few warning flags.

PG1, the same tree with the probes answered. On gpc, an x86-64 machine with 32 cores, using gcc-16 16.2.0 and rucc 0.11.18 at tamnd/rucc@9615dc28, autoconf and `-j32`:

- Both compilers built all 1423 translation units at `-O0` and at `-O2` with no failures. rucc's largest compile is `gram.c`, at 245 MB peak RSS at `-O0` and 301 MB at `-O2`, against gcc's 158 MB and 224 MB.
- `rpg config-diff` between the gcc-16 and rucc trees finds one difference at each level, `PG_VERSION_STR`, which `config-divergences.toml` explains. `pg_config.h`, `Makefile.global` and every configure answer are otherwise the same, including `__get_cpuid`, `__get_cpuid_count`, the SSE 4.2 and AVX-512 intrinsics and `popcntq`, so a rucc build now compiles the same CRC32C and popcount choosers gcc's does.
